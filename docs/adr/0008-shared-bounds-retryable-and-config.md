# 0008: Shared bounds, retryable meaning, configuration summary and cleanup

Strings, idempotency keys, webhook bodies and provider response bodies are bounded by the shared functions `boundedString`, `validateIdempotencyKey` and `readBoundedText`. An idempotency key is 1 to 128 characters from `[A-Za-z0-9_-]`; the former minimum of 10 rejected short keys without preventing any collision. `readBoundedText` rejects a body whose `content-length` or streamed byte count exceeds its limit, rejects bytes that are not well-formed UTF-8, and keeps a leading byte order mark so the webhook HMAC is computed over the received bytes. The webhook route answers 400 for both rejections; 413 is not used, because one status for every unreadable body is enough for a provider retry decision. Provider requests set `redirect: "manual"`, raise `RAZORPAY_INVALID_RESPONSE` for a 3xx, abort after 10 seconds, and read at most 4194304 bytes.

`retryable` is `true` only when a failure may be transient (network failure, timeout, 408, 429 or 5xx) and the identical call is repeat-safe (a read, a component- or provider-deduplicated key, 429 or a failure before sending). Keyed order, customer, plan and subscription creates reconcile pending claims by the scoped `operatornestIdempotencyKey` note before another POST; every refund carries `X-Refund-Idempotency`; Razorpay captures a payment at most once. Every other 4xx has retryable false. A definitive create refusal excludes 408, 409 and 429 and can fail a claim without making an identical retry eligible. An unkeyed create, a customer edit and a subscription cancel, pause, resume or update have retryable false after a network failure, timeout or 5xx. Invalid responses carry no retryable field.

Stored pagination cursors contain at most the index's declared fields plus _creationTime and _id: 4 values for payments.list and 5 for subscriptions.list. Shorter cursors remain valid prefix bounds. Both cursor and endCursor use the same bound; page reads retain their row and byte budgets.

`config.get` returns the effective test mode, whether calls are simulated, the key ID and which secrets are set, so an app can check its deployment without reading component env; it returns no secret. Retention runs as the internal mutation `cleanup.run` from the daily cron `"cleanup"`, deleting webhook receipts in batches of 100 and rescheduling itself while a batch fills. The webhook route is registered only through `client.registerRoutes`, so one registration path carries the client's onEvent default.
